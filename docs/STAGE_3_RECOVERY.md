# Stage 3: free-plan backup and recovery

D1 remains the live authority. This implementation requires no paid Cloudflare product. The owner's selected alternative to a paid cloud backup bucket is a dated encrypted PC copy plus a private Google Drive copy. Google Drive connection and remote upload verification must be completed before claiming three independent copies. A synchronized folder is a transport; never propagate deletions from D1 into dated backup files.

## Coverage and encryption

Scheduled exports now gzip the full business snapshot before AES-GCM encryption using an authenticated version-2 envelope. Readers retain support for existing version-1 archives. Compression preserves all records and history; it does not prune old orders. Compressed payload decoding has a 64 MiB expanded-size bound. Existing archives are preserved unchanged. No automatic deletion or retention pruning is enabled; select and approve a retention policy separately.

The public backup information site is deployed separately with `wrangler.backup-info.jsonc` at `https://jinam-backup-information.jinampanc.workers.dev`, because the business app is protected by Cloudflare Access. Its information, privacy and operating-limit pages are `/backup-info.html`, `/backup-privacy.html` and `/backup-terms.html`. Direct desktop authorization is prepared with `node scripts/authorize-drive-backup.mjs <private-config.json> <owner-downloaded-desktop-client.json>`. It uses loopback OAuth with state and PKCE, requests only `drive.file`, saves credentials beside the private config and creates an app-owned private folder. Do not authorize a Testing-mode Google application as a permanent unattended installation: complete Google's production configuration first. Failed folder creation can retry using the saved private credential without replacing it. No connector credential is reused.

The versioned business archive includes 14 operational tables: orders and order history; preferences; clients; billing documents (including invoices, challans, quotations and receipts represented by these documents); payments and their history; label tasks, templates, layouts, presets and history; shared product/commerce collections and their changes; MeTh stock, fulfilment policy and routing claims. IDs, numbering (including deleted-record sequence high-water counters in new archives), JSON fields, archived states, tombstones and original histories are preserved. Passwords, memberships, sessions, passkeys, OAuth state, connector secrets and security events are excluded. Rebuild accounts and reconnect integrations through a separate security-admin recovery process. Application code and repository assets are recovered from GitHub. Unsaved browser drafts and offline scan queues are not D1 records and are not included in scheduled exports.

Files use AES-256-GCM with a random salt and nonce, PBKDF2-SHA256 (100,000 iterations), an authenticated format marker and an internal SHA-256 manifest. Backup passphrases never go to the application's server. Keep the recovery key separately from the encrypted backups and from Google Drive. Losing every copy of the key makes encrypted backups unrecoverable. The local scheduled runner reads a private owner-controlled key file; do not commit that file or configuration.

## Owner download and restore

The primary screen now shows owner-checked D1 counts and last verified PC/Drive receipts. Receipts are historical evidence, not proof a device or Drive file is currently reachable. Signing in on another device is not counted as a backup. `scripts/backup-status.mjs <private-config> <manifest>` reopens and rehearses the encrypted file before publishing metadata-only receipts to the existing immutable backup-operation log. A Drive receipt additionally requires its recorded byte hash, cloud identity and verification date. No customer records or recovery keys enter those receipts. Publication failures leave every encrypted copy intact.

Owner-managed download, archive unlock and recovery preview use the existing backup format with a protected Worker secret named `BACKUP_RECOVERY_KEY`. Provision the existing private key after destination-specific owner approval; never regenerate it merely to enable the screen, and never put it in D1, repository files or logs. The key is not returned by the API. Every managed export/unlock requires current owner membership in all three businesses and an ERP session created within the last ten minutes. Archive files in this mode are sent to Jinam's recovery service for authenticated decryption, then displayed read-only. Advanced recovery retains local/offline passphrase-based tools. Managed mode requires D1 authentication availability; it is not independent recovery of lost accounts or a dead Cloudflare service.

Keep another protected key copy independently of this PC and Cloudflare before relying on managed recovery. GitHub encrypted Actions secrets are an owner-approved possible custody location, but provisioning and access recovery must be verified; do not claim that copy exists before checking it. Encryption cannot be recovered from the archive alone. Automatic Drive discovery, independent daily scheduling and a replacement live database are separate outstanding work.

Open Settings → Backup & recovery, or `/backups`. Whole-system export requires fresh server-checked owner membership in all three businesses. The browser encrypts the returned archive, then prepares a download. A prepared download is not proof the owner saved the file.

Select a backup to authenticate encryption and checksum, verify the migration version and compare new, duplicate and changed records. No business records change during this dry run. The initial restore path intentionally accepts only an empty operational database; it never merges or overwrites existing/newer records. Restoring requires an ERP login less than ten minutes old and the exact confirmation `RESTORE EMPTY SYSTEM`. A D1 transaction checks emptiness again, imports history before entities and appends a restore event. Constraint errors and concurrent inserts roll the entire restore back. Existing accounts are retained; security credentials are never imported. History contains the original archived events plus new insertion events from recovery. Reload open devices after recovery.

Large archives exceeding the 16 MB request limit, 1.8 MB row/chunk bound or 19-statement free-plan transaction budget require isolated recovery with the local tool. These limits are refusals, not partial import.

## Periodic PC copy

Create an owner-only private configuration outside the repository:

```json
{
  "directory": "<absolute backup folder>",
  "keyFile": "<absolute private recovery key file>",
  "xdgConfigHome": "<authorized Wrangler configuration directory>",
  "driveDirectory": "<optional verified Google Drive desktop sync folder>"
}
```

Run `node scripts/business-backup.mjs export <private-config.json>`. Wrangler must already be authorized to read/export the database. An expired login or disconnected drive causes a visible failure; it does not replace the prior successful backup. Wrangler's signed raw-export URLs are captured and never logged. The raw full SQL exists only in a temporary directory during export, is processed in memory, and is removed in a checked cleanup path. Only the sanitized encrypted archive is retained or sent to Drive.

Every successful backup is decrypted and restored into a fresh in-memory SQLite database, with exact table/row comparisons and `PRAGMA integrity_check`. Only then is the `.partial` file renamed into the dated final archive and a metadata-only manifest/operations log recorded. No retention deletion is automatic. Monitor disk and Google Drive capacity; preserve at least daily, weekly and monthly copies manually until a retention policy is explicitly selected. The optional Drive folder copy verifies local file bytes; it does not prove Google's remote synchronization completed.

The replacement PC runner is `scripts/pc-backup.mjs`. `scripts/install-pc-backup.ps1` installs a native Windows task at 20:00 local time, plus a logon catch-up trigger. It runs using the existing Windows login and a standalone Node executable, without Codex or Jinam being open. Windows must be on and the user logged in; Internet and valid D1 authorization are required for a fresh server export. The runner records local and Drive results independently in `pc-status.json`, preserves prior files, retries failed Drive copies without repeating today's verified export, and logs native runs in `pc-job.log`. A missed run can catch up after logon. Registration must be performed through a Windows session allowed to access Task Scheduler.

The independent cloud path is `.github/workflows/business-backup.yml`: daily at approximately 20:17 India time, with manual dispatch. It exports, encrypts and rehearses recovery on a GitHub runner, then verifies both archive and manifest by downloading their bytes from private Google Drive storage. The PC, Codex and Jinam may all be closed. It requires direct Jinam Google authorization and a dedicated Cloudflare D1 export token. Codex connector credentials are never reused. The workflow stays disabled until repository variable `SEIKO_CLOUD_BACKUP_ENABLED` is `true`. Use the exact secret and variable names in the workflow; never paste credentials into issues, chat, repository files or public logs. The recovery key in GitHub encrypted secrets is a deliberate additional custody location and requires owner approval before provisioning. Google OAuth testing credentials can expire; configure an appropriate production OAuth application before relying on unattended refresh.

Standard GitHub-hosted runners in this public repository require no paid Cloudflare service. GitHub scheduled runs can be delayed and are automatically disabled after 60 days without repository activity. See [GitHub schedule rules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). Monitor failed runs and schedule health. If Google Drive is unavailable, the PC copy can still succeed; if the PC is unavailable, the cloud job can still succeed. Neither path can produce a fresh D1 snapshot during a D1 outage. No automatic retention deletion is enabled.

For optional direct Drive upload from the PC, add `googleDrive: { "credentialsFile": "<private OAuth JSON path>", "folderId": "<dedicated private folder ID>" }` to private configuration. The credentials JSON contains `clientId`, `clientSecret`, and `refreshToken`. Create a dedicated app-owned folder when using `drive.file` scope. The uploader refuses public/shared folders, duplicate filenames, mismatched existing bytes and unexpected upload destinations. A desktop sync folder alone does not prove a remote backup.

Implementation status on 5 October 2026: the standalone PC runner produced a verified production snapshot; independent provider-failure tests and offline browser recovery tests passed. Native task installation was refused with Access denied by Windows Task Scheduler. Direct cloud credentials have not yet been provisioned, so cloud scheduling is not enabled. The previous Codex heartbeat remains active until its replacement is verified; it must then be paused through the automation tool. This is not yet a fully unattended independent backup installation.

While `/backups` is already loaded, Download local recovery copy also works without Internet. It encrypts available operational localStorage caches and pending changes in a separate `.jinam-local-recovery` format and excludes credential keys. It does not contain a complete D1 database, unsaved component state or all browser storage. Local copies can be checked offline and cannot be passed to the D1 restore action. Fresh page loading while offline is not promised.

## Search saved archives

The Backup & recovery page provides read-only archive browsing. Enter the backup passphrase, select one or more encrypted `.seiko-backup` files (48 MB combined maximum), select a record type, and search any saved value. Expand a result to inspect its complete saved record and its source filename/snapshot date. Decryption and checksum validation happen locally; browsing makes no backup API request, works while the page is already open offline, and changes no live records. Wrong keys or invalid archives clear the prior selection and refuse browsing. Close archives removes the displayed decrypted data from application state. This does not automatically discover Drive files or copies on other devices, provide a replacement live database, or recover changes newer than a snapshot. Owners must download the encrypted files to the current device first. Results from multiple snapshots remain separate so older versions are not silently merged.

## Independent Mac copy

On each Mac, keep a checkout of the committed repository and install its locked dependencies with Node 22.13 or newer. Securely transfer the existing recovery key to that Mac; do not generate a replacement key or transfer Windows configuration paths. Prepare a private configuration with absolute Mac paths for `directory`, `keyFile` and the authorized Wrangler configuration directory. Authorize D1 export on that Mac once. Direct Drive upload additionally needs its dedicated OAuth credentials; a Codex connector is not a substitute.

Run `node scripts/install-mac-backup.mjs /absolute/private/config.json` from the Mac's normal login, without sudo. The installer restricts the configuration and key to the current account, validates a user LaunchAgent, runs and verifies the first backup, and only then registers `com.jinam.daily-backup`. The job runs at 20:00 local Mac time and at login; a 30-minute catch-up/retry interval reuses today's verified archive instead of exporting it repeatedly. It uses the standalone Node runtime and committed backup runner, without Codex or Jinam being open. Preserve the checkout and Node executable at their configured paths. The Mac must be awake, signed in and online for a fresh D1 export. The independent cloud job is the copy that can run while all personal computers are off.

The Mac installer has automated schedule-generation and platform/path guard tests. Installation and a real export must be verified on the actual Mac before counting it as a backup device. No Mac is configured merely by signing in to Jinam.

On 7 October 2026, Windows owner setup reported the native task ready and a completed first run. The local status records 232 business rows across 14 tables, numbering counters included and integrity `ok`. Direct Google Drive authorization remains absent; neither unattended Drive upload nor the independent cloud job is claimed enabled.

## Restore drill

Run `node scripts/business-backup.mjs drill <private-config.json> <archive.seiko-backup> <new-local.sqlite>`. It refuses an existing target file and never connects a restore to production D1. It creates the committed schema, replays exact business records and histories in an isolated transaction and reinstalls audit triggers. The report records archive checksum, record count and integrity result. Keep this report with the archive manifest. After a future schema change, run a new drill before relying on older archives; migration compatibility must be reviewed rather than silently guessed.

Production recovery must first preserve the current D1 database and accounts, rehearse the chosen archive locally, review its date/counts, and use the authenticated empty-system restore. Do not delete live tables to make the restore button available. Recovery to the latest backup excludes changes made after that backup and unsynced browser changes.
